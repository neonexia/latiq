# Lineage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every query a pond serves emits an OpenLineage event into a per-pond store that agents can query in SQL as `lineage.events`, mid-run, with no network and no external service.

**Architecture:** Events are appended as files in the pond's own directory. A tiny per-pond `lineage.duckdb` — written **once** at pond creation, never again — holds a single view over those files and is `ATTACH`ed `READ_ONLY` into every pond connection. The view's glob re-evaluates per query, so new events appear immediately with no second writer on any database and no lock contention. A background compactor rewrites batches into Parquet. An optional OpenLineage HTTP sink is additive.

**Tech Stack:** Rust, DuckDB (`read_json_auto` / `read_parquet` over a glob), `serde_json`, `reqwest` (already in the tree).

**Design source:** [`docs/lineage.md`](../../lineage.md). Read it first — especially *Decisions* and *Read-only is defence in depth, not a boundary*.

---

## Settled before implementation

| Decision | Rationale |
|---|---|
| **One sidecar per pond**, not per node | Authorization does not exist; a node-wide sidecar would show every pond's provenance to every agent, and filtering would be advisory rather than structural |
| **Reads emit as well as writes** | A write-only graph answers who *produced* a dataset but never who *consumed* it |
| **Reaped with the pond** | `LocalFs::drop_pond` already does `remove_dir_all` on the pond directory — zero new lifecycle code. Cost accepted: dropping a pond destroys its provenance; the HTTP sink is the durability answer |
| **View over files, not a node-owned table** | A read-only attach **pins a snapshot at attach time** — measured: the writer inserts, the reader never sees it, and only `DETACH`+re-`ATTACH` refreshes. Refreshing per query would mutate database state shared by every pooled read connection |
| **No write-path guard in this slice** | `write_query` runs arbitrary SQL (#53), so an agent can forge or destroy events. M1 assumes trusted agents; **[#79](https://github.com/neonexia/latiq/issues/79)** tracks the per-pond sandbox and is a prerequisite for beta, not for this slice. Do not write "an agent cannot rewrite its provenance" anywhere |

Measured constraints that shape the code — all from a throwaway experiment against a real `PondInstance`, DuckDB 1.10503.1:

- `CREATE VIEW` **fails** on a glob matching no files (`IO Error: No files found that match the pattern`). A fresh pond needs a seeded sentinel event.
- `SELECT *` is **not a stable schema**: column count, order and types re-bind per query from whatever files exist, and a conflicting type silently rewrites earlier rows (`r1` became `"r1"`). Pin an explicit column list.
- **~0.11 ms per file**, no warm-up: 50 files 17.9 ms, 500 files 65 ms, 5000 files 1130 ms. One Parquet is 1.2 ms flat regardless of row count. Batching and compaction are mandatory, not optimisations.
- A **torn write breaks the view for every reader** (`Malformed JSON in file …`). Write to a temp file and rename.
- `information_schema.tables` has **no `database_name` column** in this DuckDB — use `table_catalog`.

## Task 5: Emit events from the query path

**Files:** `crates/latiq-agent-core/src/ops.rs`, `src/lineage.rs` (new, mirroring `access.rs`)

- [ ] **Step 1: Understand the seam before writing code**

Every op in `ops.rs` splits into a public method (resolves the pond, decides forwarding, audits) and a private `*_local`. Emit in the **public** method, beside `self.audit(...)`, where identity, pond id, redacted SQL, duration and outcome are all in scope.

**Emit only on the local path.** A forwarded op returns early — *"The owner audits + snapshots; we just return its result, so attribution stays on the node that ran it."* Emitting on both sides produces duplicate events with different pond-local snapshot ids.

Two constraints inherited from the access trail, both already documented in `ops.rs`:

- **`read_arrow` records at establishment, not completion.** Completion is unobservable on both paths, and "an audit record must not be contingent on the behaviour of the party being audited". So its event's `duration_ms` measures establishment and `outcome` says the read *started*. Say this in a comment; do not silently imply otherwise.
- **`read_collected` calls `read_arrow_local`.** Emit in public methods only, or one call produces two events.

## Task 6b: Reads carry an exact snapshot version

**Files:** `crates/latiq-engine-duckdb/src/exec.rs`

Settled by measurement, not assumption — and the result inverts the concern that
prompted it.

**DuckLake has a direct accessor: `SELECT id FROM <cat>.current_snapshot()`.** No
scan, and — the part that matters — **inside an explicit transaction it returns the
transaction's pinned snapshot, not the global newest**, regardless of statement
order. Observed with two connections on one instance:

```
A in-txn before B writes:  current_snapshot()=2  count(t)=1
B commits:                 B current_snapshot()=3
A still in same txn:       current_snapshot()=2  count(t)=1   <-- pinned
A after COMMIT:            current_snapshot()=3  count(t)=2
```

So the version recorded is genuinely the one the read observed. Unbracketed, each
statement resolves independently and the value *is* the approximation we feared —
confirmed: an unbracketed accessor reported 4 for a read that had seen 3.

**And it is cheaper than what we ship today** (200 iterations, 200k-row read, release):

| shape | per-iteration |
|---|---|
| plain read (today, no version) | 2.13 ms |
| read + unbracketed `current_snapshot()` | 2.46 ms |
| **`BEGIN READ ONLY` + read + `current_snapshot()` + `COMMIT`** | **1.90 ms** |

Auto-commit re-resolves the DuckLake catalog snapshot for every statement; one
transaction amortises that across the read and the accessor. `current_snapshot()`
is also ~2× cheaper than `max(snapshot_id) FROM snapshots()`, which scans the list.
The "extra round trip on the hot path" objection does not survive the numbers.

    // connection, commit a write on another, and assert the read's reported

- [ ] **Step 2: Implement**

Add `current_snapshot(inst, cat_quoted) -> Option<i64>` beside the existing
`max_snapshot`. **Keep `max_snapshot` for the write path** — that path compares
before/after across a commit boundary, where "global max" is the right question.

In `run_read` and `run_read_arrow`: `BEGIN TRANSACTION READ ONLY` → the read →
`current_snapshot()` → `COMMIT`, with `ROLLBACK` on every error path. Follow the
discipline `run_write` already uses — a dangling open transaction wedges the
pooled connection, and these connections are reused.

Two cautions specific to `run_read_arrow`:
- The transaction stays open across the whole batch stream. That is a correctness
  *gain* — the stream becomes snapshot-consistent instead of per-fetch — but it
  means the cancellation path must `ROLLBACK` after the interrupt, alongside the
  existing discard/reset.
- Pinning is **lazy**: it happens at the first catalog-touching statement, not at
  `BEGIN`. Harmless here, since whichever of the read or the accessor runs first
  establishes the pin and the other agrees.

**Caveat to verify before relying on this in the gatewayed cluster:** the pinning
behaviour was confirmed only against a **local DuckDB metadata catalog**,
single-node. With a remote/shared metadata catalog (Postgres/MySQL-backed),
multi-writer isolation semantics could differ. Confirm before the multi-node e2e.

**Free bonus, deliberately NOT taken here:** `BEGIN TRANSACTION READ ONLY` is
**engine-enforced** — a write inside one fails with `Cannot write to database
"pond" - transaction is launched in read-only mode`. `crates/latiq-engine-duckdb/CLAUDE.md`
currently documents the read/write guard as a text heuristic (`is_read_only`)
precisely because "DuckDB exposes no statement-type introspection". This is that
introspection, arriving from a different direction. Demoting `is_read_only` from
gate to fast-fail hint is a real improvement and a separate change — flag it, do
not bundle it.

## Task 7: Compaction

**Files:** `crates/latiq-lineage/src/compact.rs`, `crates/latiq-pond-node/src/lib.rs`

- [ ] **Step 1: The measurement that makes this mandatory**

~0.11 ms per file, no warm-up. 50 files → 17.9 ms; 500 → 65 ms; 5000 → 1130 ms. One Parquet is **1.2 ms flat regardless of row count**. With reads emitting, a busy pond reaches thousands of files in an afternoon and every lineage query pays for it. Compaction is not an optimisation.

Compaction under a live view was measured safe: writing new Parquet then rename-plus-delete of the old files was picked up immediately and correctly.

- [ ] **Step 2: Write the failing test**

```rust

    // Assert the row set is IDENTICAL before and after -- compaction that
    // loses or reorders events is worse than no compaction. And assert the
    // file count actually dropped, so the test cannot pass by doing nothing.
}
```

- [ ] **Step 3: Implement**

A background task on the pond node, modelled on the existing `spawn_node_collector` / heartbeat loops (`tokio::spawn` + `sleep`, with `Err(e) => tracing::warn!` and never propagating). Every N seconds, for each open pond: if the JSONL file count exceeds a threshold, write the union to one Parquet, then delete the sources. **New file first, delete second** — the reverse loses events if the process dies mid-compaction.

The view's `read_json_auto` glob must become a union over both `*.jsonl` and `*.parquet`, or compaction makes events vanish. Update the view definition in Task 3's `sidecar::create` accordingly, and add a test that events survive **spanning both formats**.

DuckDB writes are blocking — run the compactor on `spawn_blocking` or a dedicated thread, per `latiq-agent-core/CLAUDE.md`.

**Design coverage:** per-pond sidecar (1, 3, 4), reads+writes emit (5), reaped with the pond (1), view-over-files with stable schema and seed (3), batching and compaction (2, 7), HTTP sink (8), identity with `verified` in the event (5), snapshot id as version (5, 6), parent-run as claimed (2).

**Not in this slice:** the write-path guard. Lineage's read-only property is defence in depth only until [#79](https://github.com/neonexia/latiq/issues/79) lands. That is a prerequisite for beta, not for this plan.
