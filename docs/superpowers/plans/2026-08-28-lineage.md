# Lineage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every query a lineage-enabled pond serves emits a **spec-compliant OpenLineage `RunEvent`**, written to files in the pond's own directory, fetchable by agents over MCP and pushable to any OpenLineage backend.

**Architecture:** Events are canonical `RunEvent` JSON, one per line, batched into files under `<pond>/lineage/`. No sidecar database, no attached catalog, no view. Agents fetch events with an MCP tool that returns them verbatim; enterprise tools receive them through an optional HTTP sink. Files are reaped with the pond.

**Tech Stack:** Rust, `serde_json`, `reqwest` (already in the tree), `uuid` (needs `v5` added).

**Design source:** [`docs/lineage.md`](../../lineage.md). Read it first.

---

## Scope decision — read this before touching anything

An earlier draft built a per-pond DuckDB sidecar holding a view over the event files, attached `READ_ONLY` so agents could `SELECT * FROM lineage.events`. **That is deliberately cut.** Publish compliant OpenLineage first; optimise access later.

What the cut removes: the sidecar catalog, the view, the seeded sentinel, the pinned column list, the read-only attach, an extra attached database per open pond — **and any need to amend invariant 6**, since nothing Latiq-owned goes near the pond's catalog.

What it costs, stated so nobody rediscovers it as a surprise: an agent wanting to filter or aggregate lineage either pulls events through the MCP tool and does it itself, or writes its own `read_json_auto` over the directory — where the facets map, being different in every event, will struct-unify and shift the inferred schema between queries. That is a real ergonomic cost and it is why the catalog existed. Revisit with evidence that agents need it; a view over these same files is purely additive and nothing here forecloses it.

## Settled before implementation

| Decision | Rationale |
|---|---|
| **Opt-in per pond, default OFF** ✅ done | Lineage costs disk and ~380 µs of plan extraction per query. A pond property, not a node setting — the default deployment pays nothing |
| **Fixed for the pond's lifetime** ✅ done | No enable/disable RPC. Enabling later leaves a gap that reads as "nothing happened" rather than "we were not recording" |
| **Reads emit as well as writes** | A write-only graph answers who *produced* a dataset but never who *consumed* it |
| **Reaped with the pond** | `LocalFs::drop_pond` already does `remove_dir_all`. Cost accepted: dropping a pond destroys its provenance; the HTTP sink is the durability answer |
| **Files + MCP tool, no catalog** | See *Scope decision* |
| **No write-path guard in this slice** | `write_query` runs arbitrary SQL (#53), so an agent can forge or destroy event files. M1 assumes trusted agents; **[#79](https://github.com/neonexia/latiq/issues/79)** is a prerequisite for beta. **Do not write "an agent cannot rewrite its provenance" anywhere** |

## OpenLineage compliance — non-negotiable, and mostly settled

The event must be a real `RunEvent` (spec **2-0-2**), not a Latiq-shaped struct. Established by research; the details below are load-bearing.

**Envelope.** Required: `eventTime`, `producer`, `schemaURL`, `run`, `job`. `eventTime` is RFC-3339 **with an explicit offset** (`2026-08-29T14:22:07.481Z`) — a naive local timestamp is invalid. `eventType` ∈ `START | RUNNING | COMPLETE | ABORT | FAIL | OTHER`. `run.runId` must be a **UUID**.

**Every facet — standard or custom — requires `_producer` and `_schemaURL`.** Missing either is one of only two hard rejection causes (the other being a non-UUID `runId`).

**Use the standard facets. Do not invent replacements:**

| Need | Facet | Attaches to | Key |
|---|---|---|---|
| claimed workflow/step | `ParentRunFacet` | `run.facets` | `parent` |
| redacted SQL | `SQLJobFacet` (+ `dialect: "duckdb"`) | `job.facets` | `sql` |
| **DuckLake snapshot id** | `DatasetVersionDatasetFacet` | each input/output | `version` |
| failure | `ErrorMessageRunFacet` | `run.facets` | `errorMessage` |
| classification | `JobTypeJobFacet` | `job.facets` | `jobType` |
| engine version | `ProcessingEngineRunFacet` | `run.facets` | `processing_engine` |

`datasetVersion` is a **string** — stringify the `i64` snapshot. This replaces any top-level `snapshot_id` field.

**Custom facets**, prefix `latiq`: `latiq_identity` (run) carrying `verified`/`subject`/`issuer`/`agentId` plus a hard-coded `agentIdVerified: false`; `latiq_pond` (job) carrying `pondId`/`pondName`/`nodeId`; `latiq_query` (run) carrying `op`/`outcome`/`durationMs`/`durationMeaning`/`traceId`. Consumers ignore unknown facets by design — confirmed against Marquez and DataHub.

**The parent-run gotcha.** `parent.run.runId` must be a UUID, but a caller's `workflow_id` is an opaque string. Derive a **UUIDv5** from it under a fixed Latiq namespace so the same claimed workflow always maps to the same parent run, and carry the raw strings verbatim in a `latiq_parent_claim` facet with `verified: false`. Never fabricate silently.

**Naming — our conventions, because the spec is silent on DuckDB.** Say so in comments:
- `job.namespace`: `"latiq"` (one per deployment). **Not** the pond — ponds are ephemeral and Marquez treats a namespace as a top-level object.
- `job.name`: `{pond_name}.{op}.{schema}.{table}` for writes, `{pond_name}.{op}.{first input}` for reads, `{pond_name}.{op}` when nothing resolves. The target's leading catalog segment is dropped when it equals the pond name (it always does for a pond's own table), and kept when it does not. It must recur across runs, so it must never contain the run id, a timestamp, or the SQL.
- dataset `namespace`: `ducklake://{pond_id}`, `name`: `{catalog}.{schema}.{table}`. External sources use the **standard** schemes (`s3://{bucket}`, `file`) unmodified — those are what another tool joins on.

**START/COMPLETE.** The spec requires one `START` and one terminal event per run. Emit both, into the same batch. For `read_arrow` both fire at establishment, with `durationMeaning: "establishment"` and no row count — the honesty lives in the labelled facet, not in withholding the event. A lone `START` would leave a permanently-`RUNNING` run in every Marquez we ship to.

## Task 3: Emit from the query path

**Files:** `crates/latiq-agent-core/src/{lineage.rs,ops.rs}`

- [ ] **Step 1: Understand the seam first**

Every op in `ops.rs` splits into a public method (resolves the pond, decides forwarding, audits) and a private `*_local`. Emit in the **public** method, beside `self.audit(...)`, where identity, pond, redacted SQL, duration and outcome are all in scope.

**Emit only on the local path.** A forwarded op returns early — the owner audits, so the owner emits. Emitting on both sides produces duplicate events with different pond-local snapshot ids.

Two constraints inherited from the access trail, both already documented in `ops.rs`:
- **`read_arrow` records at establishment.** Completion is unobservable on both paths, and an audit record must not be contingent on the behaviour of the party being audited.
- **`read_collected` calls `read_arrow_local`.** Emit in public methods only, or one call emits twice.

## Task 4: Inputs and outputs from DuckDB's bound plan

**Files:** `crates/latiq-engine/src/engine.rs`, `crates/latiq-engine-duckdb/src/exec.rs`, `crates/latiq-common/src/meta.rs`

**Use `json_serialize_plan`, NOT `json_serialize_sql`.** Settled by investigation:

- **Views.** For `SELECT * FROM v` where `v` joins `a` and `b`, the parse tree returns `"table_name":"v"` and base tables are unrecoverable. The bound plan returns `pond.main.a` and `pond.main.b`. CTEs resolve the same way.
- **Writes.** `json_serialize_sql` refuses them: *"Only SELECT statements can be serialized to json!"*. Disqualifying.
- **Per-input versions free.** Every DuckLake scan carries `"snapshot":{"snapshot_id":8}`, which maps 1:1 onto each input's `DatasetVersionDatasetFacet`.

Verified: it **never raises** (returns `{"error":true,…}`), **does not execute** (checked against `INSERT`, `DELETE`, `DROP`, `COPY … TO` — row counts, snapshot ids and the `COPY` target all unchanged), and costs ~380 µs against a 2.16 ms query.

**Rejected, recorded so nobody re-litigates:** the purpose-built C API `duckdb_get_table_names` **silently returns no tables** for `USING` joins, `NATURAL` joins, every `UPDATE` and every `DELETE` — silent under-reporting is the worst failure mode for provenance. `EXPLAIN (FORMAT JSON)` emits bare table names for DuckLake scans, conflating catalogs. Profiling requires executing the statement.

`exec.rs::referenced_tables(inst, sql) -> (Vec<TableRef>, Vec<TableRef>)`.

**Pass the SQL as a bound parameter with an explicit cast** — `SELECT json_serialize_plan(?::VARCHAR)`. A bare `?` is rejected. This removes the escaping and injection surface; never concatenate.

Walking the JSON: **key names differ by table function** — `ducklake_scan` uses `catalog_name`/`schema_name`/`table_name` (+ `snapshot.snapshot_id`), core `seq_scan` uses `catalog`/`schema`/`table`, `read_parquet` carries `files`. ## Task 5: Reads carry an exact snapshot version

**Files:** `crates/latiq-engine-duckdb/src/exec.rs`

Settled by measurement, and it inverts the concern that prompted it.

`SELECT id FROM <cat>.current_snapshot()` is a direct accessor, and **inside an explicit transaction it returns the transaction's pinned snapshot**, so the recorded version is genuinely what the read observed:

```
A in-txn before B writes:  current_snapshot()=2  count=1
B commits:                 B current_snapshot()=3
A still in same txn:       current_snapshot()=2  count=1   <-- pinned
```

Unbracketed, each statement resolves independently — the approximation we feared, and real (an unbracketed accessor reported 4 for a read that had seen 3).

**And it is faster than what we ship today** (200 iterations, 200k-row read, release):

| shape | per-iteration |
|---|---|
| plain read today, no version | 2.13 ms |
| **`BEGIN READ ONLY` + read + `current_snapshot()` + `COMMIT`** | **1.90 ms** |

Auto-commit re-resolves the catalog snapshot per statement; one transaction amortises it.

- [ ] **Step 1: Failing test**

```rust
#[test]
fn lineage_read_reports_the_snapshot_it_actually_saw() {
    // Open a read transaction on one pooled connection, commit a write on
    // another, assert the reported version matches the ROWS RETURNED and not
    // the newer snapshot. This is what catches a regression to unbracketed max().
}
```

- [ ] **Step 2: Implement**

Add `current_snapshot(...)` beside `max_snapshot`; **keep `max_snapshot` for the write path**, which compares before/after across a commit boundary where "global max" is the right question.

`run_read` / `run_read_arrow`: `BEGIN TRANSACTION READ ONLY` → read → `current_snapshot()` → `COMMIT`, with `ROLLBACK` on every error path — a dangling transaction wedges the pooled connection. For `read_arrow` the transaction stays open across the batch stream (a correctness *gain*: the stream becomes snapshot-consistent), so the cancellation path must `ROLLBACK` after the interrupt.

Pinning is **lazy** — taken at the first catalog-touching statement, not at `BEGIN`. Harmless: whichever of the read or the accessor runs first establishes the pin.

- [ ] **Step 3: Gate + commit** — `feat(lineage): reads report the exact snapshot they observed`

**Caveat:** confirmed only against a local DuckDB metadata catalog. With a remote/shared one, isolation semantics could differ — verify before the multi-node e2e relies on it.

**Free finding, deliberately NOT taken here:** `BEGIN TRANSACTION READ ONLY` is **engine-enforced** (a write inside one fails). `crates/latiq-engine-duckdb/CLAUDE.md` documents our read/write guard as a text heuristic *because* "DuckDB exposes no statement-type introspection" — this is that introspection. Demoting `is_read_only` to a fast-fail hint is a real improvement and a separate change. Flag it; do not bundle it.

## Deferred, with reasons

- **The SQL catalog and views** — see *Scope decision*. Purely additive over the same files.
- **Compaction to Parquet.** Was mandatory when a DuckDB view read every file (~0.11 ms per file, 5000 files → 1.1 s). With no view, file count costs the MCP tool and the sink, not query latency. Revisit if a long-lived pond makes `get_lineage` slow.
- **Column-level lineage** — a standard facet, much harder than table-level.
- ~~**`schema` facet on outputs**~~ — **shipped** after a live Marquez run showed every dataset as `"fields": []`. Covers the write target *and* every input in the pond's own catalog, in one `information_schema` lookup per statement; external datasets still carry none (we do not have their columns cheaply, and a guessed schema is worse than an absent one).

## Known-weak by construction, stated rather than hidden

`read_arrow` events carry establishment-time duration and no row count; `latiq_query.durationMeaning` makes that machine-readable rather than a comment. Table extraction is best-effort — writes are authoritative via DuckLake snapshots, inputs come from the bound plan, and unparseable SQL yields no tables rather than an error.
