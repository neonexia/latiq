# latiq-mcp — CLAUDE.md

The **MCP-over-HTTP inbound adapter** (rmcp Streamable-HTTP) onto `AgentOps`. **Agent-only.**

## Invariants
- **This surface is for agents (frontier LLMs) only.** The CLI/SDK must never call it — they use the Data/Query gRPC surface. `latiq-client` exists for agent-simulation + the MCP integration tests here.
- **Thin adapter.** Extract identity from the request, call the matching `AgentOps` method, encode the neutral result/error. No business logic — that's `agent-core`.
- **Every tool handler runs inside `LatiqServer::traced`** — the request's trace scope, its span, and its bearer scope, entered together so a handler cannot get one without the others. This surface had NO trace at all until #101 (`grep -i trace crates/latiq-mcp/src/` returned zero hits), so every agent call logged `trace_id="-"` and emitted `traceId: null`, on the one surface whose audience the product is built for. The access trail, the lineage emitter and `encode::err_envelope` all read the SAME ambient scope, so all three are served by entering it once rather than threading an id through thirteen handlers. The header is W3C `traceparent`, the same spelling the gRPC surfaces read.
- **Identity comes from the TRANSPORT, never a tool argument.** The claimed leaf is the `latiq-agent-id` HTTP header; a verified principal is `Authorization: Bearer`. No `agent_id` field on any tool schema — the model must not be able to type an identity.
- **With a verifier, auth is a LAYER in front of the router**, not a check inside handlers: every JSON-RPC method (`initialize`, `tools/list`, `resources/read`, …) is covered, and a missing/invalid token gets a real `401` + `WWW-Authenticate`, not a JSON-RPC error inside a 200. The handler only *reads* the layer's decision; the no-decision branch fails closed, never falls back to a claimed identity. Only `/.well-known/oauth-protected-resource` (RFC 9728, served here — the one HTTP surface we have) is exempt.
- **The public MCP URL is also the `Host` allow-list** (`mcp_allowed_hosts`). rmcp's Streamable-HTTP transport blocks DNS rebinding by refusing any `Host` that is not loopback — right for an MCP server on a laptop, wrong for every topology we ship, where agents dial the **gateway**. Left at rmcp's default, each JSON-RPC POST is a bare `403 Forbidden: Host header is not allowed` while RFC 9728 discovery and the 401 challenge (our own axum routes, not rmcp's) still answer — so it reads as an auth bug and isn't one. We keep rmcp's loopback entries and **add the resolved public URL's HOST** — bare, never `host:port`, because rmcp matches a port-qualified entry only against that exact port and nginx's `$host` forwards the name without one. The guard stays on and learns the real front door. A gateway that rewrites `Host` to something other than `--public-mcp-url` would break both this and discovery — don't build one.
- **Publish the URL agents dial** (`resolve_public_mcp_url`): `--public-mcp-url` behind a gateway, NOT `--advertise-addr` (the internal peer-forwarding address) and never the bound socket. A conforming client rejects a `resource` whose origin differs from the URL it dialled.
- **`get_lineage` returns events VERBATIM.** The tool is a page of the pond's own OpenLineage records (newest first), forwarded to the pond's owning node — the events are files on the node that ran the queries, so only the owner can answer. Don't round-trip them through a struct of ours: an event written by a different build of Latiq must keep every field it was recorded with. A pond allocated without `lineage` is an **error**, not an empty page — "we were not recording" and "nothing happened" are different answers.
- **Latiq owns the write transaction — say so wherever an agent reads.** `write_query`'s description, `latiq://guidance`, `latiq://dialect` and `latiq://recipes/attribution-lookup` all tell agents to send plain statements and never `BEGIN`/`COMMIT`/`ROLLBACK`/`START TRANSACTION`, because an embedded `COMMIT` ends the transaction before the author is recorded and the write lands in history unattributed. This is **guidance only** — the write path does not (and must not) scan SQL, so never write copy claiming it is rejected there.
- **Dual encoding:** results carry BOTH a text content block and `structured_content`; errors set `is_error` with the `ErrorEnvelope`. `CallToolResult`/`CallToolRequestParams` are `#[non_exhaustive]` — build via `success()/error()`/`default()` + field set, not struct literals.
- **Every tool declares an `outputSchema`, GENERATED from the type it serializes** (`schema.rs`, `response.rs`) — never hand-written, because a hand-written schema restating a struct is a second copy that nothing keeps in step. So every success goes through a type (`encode::ok`), not a `serde_json::json!` literal: a literal has no schema to derive. **rmcp does not validate responses against it** (its `model.rs` says so in as many words), so `crates/latiq/tests/mcp.rs::output_schema` drives all 13 tools to a REAL response and validates each against the DECLARED schema — without that, the declaration is a document, not a contract.
- **The declared schema is the SUCCESS shape only; the `ErrorEnvelope` is deliberately outside it.** A failed call sets `is_error`, and a client that skips output-schema validation on an error result never sees the mismatch. So one envelope shape serves all thirteen tools, and the envelope can evolve without editing thirteen `anyOf`s — each of which would also have made every success schema looser. Don't "fix" this by widening the schemas to admit the envelope. **Scope of the evidence, exactly:** the skip is verified in the two REFERENCE SDKs only — TypeScript (`&& !result.isError` on both branches) and Python (`if ... and not result.is_error`) — and is **not in the MCP spec**, so it is a fact about two implementations, not a guarantee about clients. It cannot have a test (the behaviour is in someone else's code) while being load-bearing for every error path, and it widened silently when `40cb97a` gave every tool an `outputSchema`. Nexus is settling it against **Claude Code** — a real client that is neither reference SDK — in its L0 workflow; until that reports, don't restate this as "clients skip validation".
- **A generated schema must never mark a `skip_serializing_if` field required** — a validating client would reject our own valid responses. schemars gets this right for `Option` and for `default` + `skip_serializing_if`; a field with `skip_serializing_if` and NO `default` is still required under the deserialize contract, which is the trap. Pinned by `schema.rs`'s unit tests.
- **Doc comments are stripped out of the generated schemas** (`strip_descriptions`). They ride in every `tools/list` and are paid for out of the model's context on every session; ours are written for the next engineer (issue numbers, past bugs) and cost 16 KB across the 13 tools. Structure is what an output schema is for. The strip is keyword-aware because `description` is also a real FIELD name on the dataset/catalog shapes.
- **schemars derive must target rmcp's re-export IN THIS CRATE:** `#[schemars(crate = "rmcp::schemars")]` on every arg struct and every shape in `response.rs` (else a trait-mismatch with a standalone schemars). The response types that live in `latiq-common`/`latiq-engine`/`latiq-agent-core` derive against the workspace `schemars` instead — those crates must not depend on rmcp (invariant 5) — which works only because the workspace pins the SAME schemars line rmcp re-exports. Bump one and you bump both; a skew is a build failure at the `output_schema::<T>()` call site, not a silent divergence.
- **A client disconnect does NOT reach the handler.** rmcp does not surface it: killing the client mid-stream leaves the handler running, and `Peer::notify_progress` keeps returning `Ok(())` into the dead stream. So **disconnect→abort is not a cancel source** — the cancel paths are an explicit `notifications/cancelled` and the query timeout as the backstop for an abandoned query. SSE is here for keepalive + progress, not for detecting a dropped client; never write code or docs that assume otherwise.
- **`notifications/cancelled` is wired through `RequestContext::ct`, and we do NOT match request ids ourselves.** rmcp keeps a per-request token pool keyed by request id in its serve loop and cancels the matching token when the notification arrives; `ctx.ct` is that token. It is a `tokio_util::sync::CancellationToken` — the same type as the core's `AbortToken` — so `query_controls` hands it straight to `QueryControls::with_cancel` and no protocol type crosses into `latiq-agent-core`. Building a second id→op registry here would be a copy of rmcp's, free to drift out of sync with it. rmcp does not abort the handler future, so the handler still answers — with the `query_cancelled` envelope, which is the right answer to a request the client has stopped waiting for.
- **A cancel and a timeout are the same DuckDB `INTERRUPT`, and the difference is not the engine's to know.** Both stop the query by firing the one abort token; `latiq-agent-core`'s `Deadline` remembers which fired and maps to `query_timeout` vs `query_cancelled`. Never re-derive that here from the engine's error text. And a conforming MCP client (rmcp included) resolves its own request the instant it sends the cancel and discards our response — so the `query_cancelled` envelope is NOT observable from a client, and a test that expects to read it there will be testing nothing.
- **`timeout_ms` is an optional argument on `read_query`/`write_query`** (never on `explain_query`, which does not execute). Over the maximum is CLAMPED, not refused, and `_meta.timeout_ms` reports what was applied — the tool description has to say both, because an agent that cannot see the clamp cannot understand why its query died early.
- **Root invariant 13 lands here as three concrete rules.** (1) **Every arg struct is `#[serde(deny_unknown_fields)]`** — a misspelled `timout_ms` used to be dropped in silence, so the model believed it had set a policy it had not; serde's rejection names the bad key and lists the good ones, which is the correction. (2) **An explicit `0` is refused** (`reject_zero`), on `timeout_ms` as on `get_lineage`'s `limit`: JSON can express absence, so `0` is a value the caller chose and must not be re-read as "use the default". Do not "fix" this by copying the gRPC surface's proto3 zero-means-unset — that is a wire limitation normalised at that adapter. (3) **A value that is clamped is reported** (`_meta.timeout_ms`, `limit_applied`) and a value that cannot be honoured is refused with the legal set named (`tier`, `extensions`, pond `name`). `tier` also carries a schema `enum`, so the model sees the options before it guesses.
- **Discovery is carried by the tool NAME and by the server `instructions`; descriptions teach AFTER a tool has been selected.** We claimed the opposite for months ("tool descriptions are mini-tutorials", read as if they did discovery work). Nexus measured it: driving real models against this server inside a **47-tool belt**, the client advertised all thirteen of our tools **by name** and **deferred their descriptions**, so every agent spent turn 1 fetching our schemas — after it had already decided to look at us. A tutorial fetched once the decision is made cannot inform the decision. We cannot change client behaviour, so: the **name** must stand alone (a name a model can rank without prose), and **`instructions`** (`INSTRUCTIONS` in `server.rs`, sent at `initialize`, never deferred) carries the first moves, the external-data flow, the identity rule, the error contract and the `_meta.traceparent` promise. Because the instructions are load-bearing, `instructions_name_only_tools_this_server_advertises` checks every tool-shaped name in that text against the router's own tool list: a rename must not leave an agent's *first* call pointing at a tool nobody serves (the repo already shipped a resource teaching a removed tool), and `mcp_resources_name_only_tools_this_server_advertises` does the same for every resource body.
- **A tool description is a CONTRACT, not a tutorial — the teaching lives in `latiq://` resources** (**experiment**, `experiment/lean-tool-descriptions`; revert if Nexus measures a regression). We said "keep descriptions rich" one measurement too long: the client that defers descriptions also EVICTS them under context pressure and re-fetches them, so Nexus watched an agent doing real work spend **15 `ToolSearch` round trips** against 22 `read_query` calls — eight iterations before one call landed. Rich descriptions are not free-standing; they are a per-session, sometimes per-turn, tax. So the descriptions are held to a **budget** (`mcp_tool_descriptions_stay_within_the_context_budget`: ≤2,500 bytes across all 13, ≤400 each, down from 9,390) and carry only: one line on what the tool does, its arguments, any rule whose omission **silently** costs something (write_query's `BEGIN`/`COMMIT` rule — nothing rejects it and the write lands with no author), and the resource with the rest. **Don't teach SQL or DuckDB**: a frontier model knows both, and a sentence it already knows is one it pays to hold. Everything moved must be *relocated*, never dropped — `mcp_tool_descriptions_point_at_resources_that_carry_what_they_promise` asserts the pointed-at BODY contains the moved sentence, because a link that merely resolves is how content disappears in a move.
- **Every tool result carries the call's `traceparent` in BOTH the protocol `_meta` and the response BODY's `_meta`**, set once in `encode::dual` for all thirteen. The body half exists because #113's protocol half **does not reach the model in Claude Code** — the client the agents we build for actually use. Nexus measured it: the `tool_result` block handed to the model has exactly `content`/`is_error`/`tool_use_id`/`type`, so the protocol `_meta` arrived on 0 of 3 measured calls while the body's arrived on 2 of 2 (`read_query`, the one tool whose body already had a `_meta` via `QueryMeta`). Keep both: the protocol block is correct for direct MCP clients, which do surface it. The body copy is injected in the same funnel (`encode::with_body_traceparent`) and **declared** in every generated `outputSchema` (`schema::declare_body_meta`) — a schema silent about a field we always send is the drift `outputSchema` exists to prevent — and it **never overwrites a `traceparent` already in the body**, because the query tools' is deliberately the OWNER's span. The general lesson, worth more than the fix: when a change's correctness depends on what a CLIENT does with our output, it is not verified until someone has looked at what that client delivered to the model. Until #113 only the three query tools reported one on SUCCESS (they return a `QueryMeta`, which gained `traceparent` in #110) while every FAILURE carried one — backwards, since a successful `allocate_pond` is exactly the call you later join against the lineage and access records it produced. It is set at the encoder and not on nine result structs because those live in `latiq-agent-core`, which is protocol-neutral (invariant 5), and because nine sites is nine chances to forget — which is how the gap survived #110. Both values come from `current_traceparent()`, so the trace ids agree by construction; the query tools' BODY `_meta` may name a different SPAN on a forwarded query, deliberately (`QueryMeta::traceparent` follows `served_by`). Argument refusals therefore run **inside** `traced` — an answer an agent cannot cite is worst on exactly the mistakes it has to ask about.
- **rmcp's `server` feature alone does not give you HTTP.** `transport-streamable-http-server` is required too, and `axum` must be a **direct** dependency — rmcp exposes `StreamableHttpService` as a `tower::Service` to `nest_service` into a `Router` but does not re-export axum.

## MCP is the product for agents — complete it (M10)
This surface must make a frontier agent immediately effective:
- **Tool annotations** (`read_only_hint`/`destructive_hint`/`idempotent_hint`) on every tool.
- **Lean tool descriptions** (what it does / its arguments / the silently-costly rule / the `latiq://` resource with the rest), under the budget above. The teaching they used to carry is in the resources; see the two invariants above for why, and for the guards that stop it drifting back.
- **Resources:** `latiq://guidance`, `latiq://dialect`, `latiq://datasets`, `latiq://recipes/*`, `latiq://troubleshooting/*` (the index plus one page per kind that routes to it). **Static except one section** — `RESOURCES` in `resources.rs` is the whole set, and `list_resources`/`read_resource` serve exactly it. The exception is `latiq://dialect`'s "what this pond can already read and reach", **generated from `latiq_common::extensions::EXTENSIONS`** (`capabilities()`): the page told agents at length what a pond does NOT have and nothing about what it does, and a hand-written list of nine extensions is a second copy of the shipped set — the drift that either hides a capability or advertises one no node installed. A `Res` carries `static_body` plus an optional `generated`, read through `Res::body()`; `mcp_resources_the_dialect_page_advertises_every_shipped_extension` asserts every shipped extension reaches the served body **with its state** (always loaded / ask at allocation / via `pull_catalog`), and that the hand-written halves name none of the core extensions we deliberately do not ship. There is deliberately **no `latiq://ponds` or `latiq://ponds/{id}/schema`**: this file listed them for months and neither was ever served, so an agent that believed the spec got `unknown resource`. Pond listing and schema are per-caller, need an identity, and are already **tools** (`list_ponds`, `describe_pond`) — don't re-serve them as resources.
- **A resource that states engine behaviour must have a test that RUNS it.** `latiq://recipes/schema-design` taught `CREATE TABLE (id INTEGER, -- comment)` and claimed the comment was readable; DuckDB discards a lexical `--` and stores nothing, and the claim survived in four places (recipe, guidance, `write_query`'s description, two prompts) because it was only ever proofread. `crates/latiq/tests/mcp.rs::mcp_resources_schema_design_recipe_sql_actually_stores_comments` now executes the recipe's own SQL block, read out of the served body.
- **Prompts:** the 4 SOPs (setup-multi-agent-pond, discover-existing-pond, design-collaborative-schema, recover-from-conflict).
- Errors are next-action-oriented; `see` links must resolve to a real resource.

## Tests
`tests/mcp_auth.rs` — the crate's ONE integration binary (server+client over real MCP, plus the RFC 9728 metadata/challenge tests). Every integration binary statically links a bundled DuckDB, so add tests here rather than adding a binary. Surface-level e2e: `crates/latiq/tests/mcp.rs`.
