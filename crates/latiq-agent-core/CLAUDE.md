# latiq-agent-core — CLAUDE.md

The **protocol-neutral core** of the hexagon. Holds `AgentOps` (allocate/describe/list/drop pond, read/write/explain query), the `ControlPlane` trait, the neutral result/error types, the in-flight/abort registry, the `latiq::access` emitter, the OpenLineage emitter (`src/lineage.rs`) + per-pond writer registry, and the ambient bearer task-local.

## Invariants (do not drift)
- **NO transport/protocol types here.** No `rmcp`, `tonic`/gRPC, `axum`, HTTP, or MCP types. If you're importing a protocol crate, you're in the wrong crate — it belongs in an inbound adapter (`latiq-mcp`, the Data-gRPC adapter).
- **Every external surface is an inbound adapter onto `AgentOps`.** Adding MCP/gRPC/A2A support = a new adapter crate that calls these methods. Never special-case a protocol in here.
- **`ControlPlane` is a trait** (in-process `RegistryControlPlane` for single-process/tests; `GrpcControlPlane` over the wire). `AgentOps` depends on the trait, never on a concrete transport.
- **Results are neutral** (`QueryResult { columns, rows, _meta }`, `ErrorEnvelope`). Adapters encode them; the core never knows about JSON-vs-protobuf.
- **The core consumes an `Identity`; adapters extract it from their transport.** Both modes exist: verified (`latiq-auth` produced it from a token — `subject`/`issuer` set, `verified: true`) and relaxed (`Identity::claimed`, default anonymous, the no-issuer default). Never branch on the transport in here; `agent_id` is claimed in BOTH modes and must never carry authority.
- **`bearer` is the ambient caller token** (`with_bearer` / `current_bearer`), scoped per request by each adapter and read back by the forwarder so the owning node re-verifies. Protocol-neutral by design: a bare `String` task-local, no transport types — and set ONLY when a verifier is configured.
- **`access::record` is the one `latiq::access` emitter.** Same fields from every producer (`AgentOps` and the pond node's Data/Stream adapter both call it), including `outcome` (`ok`/`error`) — audit failures and rejections, not only successes.
- **`lineage::record` is the one lineage emitter**, shaped like `access`: called from the **public** op methods beside `self.audit(...)`, so every producer says the same thing about the same operation. Four rules it must keep: **gated on the pond's `lineage` flag first** (a pond that did not opt in pays no event, no formatting, no directory lookup); **local path only** — a forwarded op returns before the emit exactly as it does before the audit, since the owner ran the query and emitting on both sides would duplicate the run under two pond-local snapshot ids; **once, from the public method** (an emitter in the local halves would record `read_collected` twice under two ops); and **it can never fail a query** — nothing here returns a `Result` and the writer swallows and warns. Datasets come from `QueryMeta.inputs`/`outputs` (the engine's bound plan); a plan that did not resolve carries no datasets rather than guessed ones.
- **One `LineageWriter` per opted-in pond**, in `ops.rs`'s `lineage_writers` map (`RwLock`, built lazily on the pond's first event). Batch writes fsync → they go to the blocking pool, never the async worker the query ran on. The optional `EventSink` is held here as a neutral trait object; the transport behind it is `latiq-lineage`'s feature-gated HTTP sink, configured only by `latiq-pond-node`.
- **Ownership is an IDENTITY comparison, never an address one.** `placement` decides local-vs-forward by comparing `AgentOps`'s own `self_node_id` (the id the node registered and heartbeats with, handed in by `with_forwarding`) against `PondInfo::node_id` (the registry's `ponds.node_id`). `node_endpoint` is only how to *dial* an owner already decided to be someone else, and `self_endpoint` is only what this node calls itself in `served_by`/lineage `nodeId` (`serving_name`). Comparing the two endpoints let one node mistake itself for another and forward into itself without bound (#89); an owner that cannot be named is `NoOwner`, never a fall back to the address. The one surviving endpoint comparison refuses to dial our own address for a foreign id — it can only refuse, never grant ownership.
- **Allocation is EAGER, and `allocate_pond` is NOT where that happens.** `ControlPlane::create_pond` returns only once the pond's storage exists on the node the control plane placed it on, because **the control plane materialises it** and rolls the placement back if it cannot (root `CLAUDE.md` invariant 3's lifecycle exception). So `allocate_pond` asks and returns — nothing else. Do not re-add a materialise step here: it would be a second call to the same node for every allocation, and `latiq pond create`/the SDK never come through `AgentOps` at all, so a mechanism living here can only ever cover some of the create paths. The compensation, its error text, and the tests that pin them are in `latiq-control-plane`.
- **`materialize_pond` is idempotent, called by the CONTROL PLANE, and routes like everything else.** Already-materialised is success, never a conflict (that is what lets a create be retried and lets the lazy `ensure_pond` on the query paths coexist with it). It is NOT a user-facing op — no CLI or SDK command reaches it — and it goes through `route`, because behind a gateway the control plane's call can land on a node that does not own the pond, which must forward rather than create a stray empty pond. `Forwarder::materialize_pond` is that forward.
- **The lazy `ensure_pond` on the query paths stays.** It is a no-op for every pond created since the control plane took over materialising (all of them go through `CreatePondAssignment`), and it is still the only thing that materialises ponds that predate this, ponds whose compensation failed, and ponds whose owner was re-provisioned with an empty disk. Dropping it turns each of those into an outage instead of a first query that costs one mkdir.
- **Engine calls are blocking** → run via `spawn_blocking`. Don't hold a std mutex guard across `.await`.

## Tests
Unit: in `src/`. Cross-component (AgentOps over RegistryControlPlane + DuckEngine + TempFs): `tests/agent_ops.rs` — the crate's one general integration binary, with `mod m7` (M7 success criteria) and `mod forwarding` (the delegation decision, over fakes) inside it. `tests/access_trail.rs` is a separate binary ONLY because it installs a process-global `tracing` subscriber; nothing else earns one, since every binary statically links a bundled DuckDB. These are the in-process feature tests; full-stack/surface tests live in `crates/latiq/tests/`.
