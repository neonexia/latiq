# latiq-engine-duckdb — CLAUDE.md

The DuckDB + DuckLake implementation of `QueryEngine`.

## Invariants
- **No `INSTALL` on a request path — ever.** Downloading an extension is an unbounded wait on an external host, and it is impossible in a deployment with no egress; a request path is the worst moment for both. `autoinstall_known_extensions` is turned **off** on every pond connection in `PondInstance::open` (not just one that requested extensions) and re-asserted at the catalog attach, and every LOAD site — the standard set, a pond's requested extensions, `attachers.rs`'s plan for an external catalog's `attach_catalog` — emits `LOAD` only. A cache miss is then an immediate failure carrying `instance::extension_not_cached(extension, context, err)` — `ErrorKind::CapabilityUnavailable`, `audience: operator`, `retryable: after_provisioning`, `facts.capability` naming the extension — not a silent download. That kind exists because the agent's call was CORRECT and the deployment is missing something: it must surface the gap to whoever orchestrates it and stop, never retry. Extensions arrive at exactly two moments, both before serving: `ensure_standard_extensions` (memoized, once per process, at node startup — kept as `INSTALL; LOAD` on purpose, because a `pip install latiq` node has no baked image and refusing to download there would mean a wheel that cannot start) and `warm_extension_cache` (`latiq warm-extensions` at image build, plus the node's background startup warm). The guards: `attachers.rs::attach_plan_never_installs_an_extension` (iterates `latiq_common::catalog::TYPES`, asserts no plan statement contains `INSTALL`) and `instance.rs::a_warmed_cache_loads_every_extension_we_ever_load_without_the_network` (warms into a scratch `extension_directory`, then LOADs everything with autoinstall off — the ambient `~/.duckdb` cache would otherwise hide a gap, which is how `avro` was missed).
- **The warm reports; the build-time command fails.** `warm_extension_cache` installs *and then verifies each extension loads offline* — "INSTALL succeeded" never meant "loads offline" (`LOAD iceberg` pulls in `avro`) — and returns a `WarmReport`. The node warns with the names; `latiq warm-extensions` **fails** on an incomplete report, so `deploy/Dockerfile` cannot build an image that silently lacks what its own comment claims. An empty `attempted` is not complete: a warm that examined nothing has proved nothing.
- **One DuckDB instance per pond** — mutex-guarded, reused across queries (cached in `DuckEngine.instances` keyed by `catalog_uri`). It's the unit of **resource isolation** (per-pond memory/CPU caps belong on the instance — DuckDB's `memory_limit`/`threads` are instance-global) and of concurrency ownership (one process owns each catalog file; independent instances racing on one catalog lose writes). NEVER revert to instance-per-query. (See the concurrency test.)
- **Attribution records provenance, not just a name.** The commit `author` is the **verified `subject`** when `identity.verified`, the claimed `agent_id` otherwise; the claimed leaf + `issuer` + `verified` always ride in `commit_extra_info` as JSON built with `serde_json` (never hand-concatenated — every value is caller- or token-supplied). A bare `verified` must never sit next to a claimed value. The request's **`trace_id`** rides there too — the join key between this always-on record and the opt-in OpenLineage events (`docs/obs.md`), so it is the BARE id the events use and not a `traceparent`. It is **omitted** when the caller had no trace scope: the engine runs on a blocking thread and cannot read the ambient scope itself, so `write_query` is HANDED an `Option<&str>`, and a `"-"`/`""`/minted id would be joined against for ever and never match.
- **Pure DuckLake — nothing on top.** Attribution = native `CALL pond.set_commit_message(author, 'write_query', extra_info => …)`. Callers read history via native `pond.snapshots()` and tables/columns via `SHOW TABLES`/`information_schema`. **Create NO Latiq objects in the pond catalog** — no `_latiq` schema, views, or macros — and no shadow store. (`describe_schema` may use `duckdb_tables()` *internally* — that's the DuckDB adapter's own introspection, not an object in the pond.)
- **There is ONE attribution bracket, and every pond-writing path goes through it** (`exec::in_write_txn`): today that is `run_write` alone, for caller SQL. An extract from an external catalog reaches it by BEING an ordinary `write_query` — the attach is separate and writes nothing — so history records it as `write_query` with the caller as author. That is the lesson, not an accident: the removed `pull_catalog` was a SECOND copy of this shape (no `BEGIN`, no `set_commit_message`) and left `(snapshot, NULL, NULL)` in `ducklake_snapshots` for months. A second copy is how one of them stops matching the other. Anything new that mutates a pond belongs inside this bracket, never beside it.
- **Write path must isolate user SQL from our framing.** Don't build a single string batch of `BEGIN; <user sql>; CALL set_commit_message; COMMIT` — user comments/`;` can comment out the COMMIT/attribution or inject statements. Execute user SQL as its own statement, then our `set_commit_message`, then COMMIT, and ROLLBACK on error. Our attribution call must be last so it can't be forged. Caller SQL that does its own `BEGIN`/`COMMIT`/`ROLLBACK`/`START TRANSACTION` closes our bracket early and the snapshot lands with **no author** — that is a **documented contract, not an enforced one**: the write path does **not** scan or classify SQL and must not start (the read guard's keyword scan exists for the read bracket only — don't mirror it here). The guidance lives on the agent-facing surfaces (`latiq-mcp` tool descriptions + `latiq://guidance`/`latiq://dialect`/`latiq://recipes/attribution-lookup`) and in `docs/identity.md`.
- **Cancellation = `Connection::interrupt_handle()`** from a watcher thread (`src/abort.rs`); on abort, interrupt + (for safety) discard/reset so a stale interrupt can't bleed into the next query on the reused connection. `abort` must release engine resources promptly (the cancellation test is the gate).
- **The interrupt must be fired REPEATEDLY, and the wait for a resource is part of the abort's job.** DuckDB's interrupt is edge-triggered against a *running* statement — the flag is cleared as each statement begins — so a single shot fired in a gap (before the operation reaches the engine, between our `BEGIN` and the caller's SQL) is silently discarded and the statement then runs with **no bound of any kind**. That is not hypothetical: nightly 33789446152 committed a write that reported `duration_ms: 2694228` under `timeout_ms: 60000`. `AbortWatcher` therefore keeps firing while the token is cancelled, and `Pond::lock_writer` polls the abort while queued for the pond's writer mutex, because an interrupt has nothing to act on there at all. Never turn either back into a one-shot. The mirror rule: `disarm` **joins** the watcher, and `write_query` re-issues `ROLLBACK` after it, because a rollback that is itself interrupted leaves the pond's one writer connection mid-transaction and wedges every later write.
- **There is no timeout here, and there must not be.** DuckDB has none of its own — searching every setting for one yields `memory_limit` and `pivot_limit`, both about size — so the deadline is `latiq-agent-core`'s `Deadline`, which fires this same abort token. That is also why `run_with_abort` normalizes `INTERRUPT` to `EngineError::Cancelled` and stops there: an expiry and a user cancel produce a byte-identical `INTERRUPT Error: Interrupted!`, so **this crate cannot tell them apart and must not guess**. The core knows which trigger it pulled and maps to `QueryTimeout` vs `QueryCancelled`. Don't add a timeout knob here, and don't try to classify the interrupt from its text.
- **`duckdb_query_progress` is NOT reachable from this crate** (checked against duckdb-rs 1.10503.1): the symbol exists in `libduckdb-sys`, but it takes a raw `duckdb_connection`, `Connection`'s `db` field and the `inner_connection` module are both private, and there is no accessor. So a timeout error cannot report "was 78% complete", and it must not invent a number. Re-check on a duckdb-rs bump before writing any progress copy.
- **`drop_pond` must evict the cached instance** (close the connection) — or it leaks fds/connections to deleted catalog files.
- **Read/write/explain guards are ours.** `read_query` must reject writes (incl. `WITH … INSERT`); `explain_query` must NOT execute (`EXPLAIN ANALYZE` runs the statement — reject it). DuckDB exposes no statement-type introspection, so these are careful heuristics — test the edge cases. The keyword scan treats `;` as a separator (without it `SELECT 1;INSERT …` passed as a read and the insert *ran*), and rejects **transaction control** (`BEGIN`/`COMMIT`/`ROLLBACK`/`ABORT`/`START TRANSACTION`/`END TRANSACTION`) because user SQL must not be able to close the bracket below. Bare `END`/`START` stay allowed on purpose — `CASE … END`.
- **The two read paths run inside `BEGIN TRANSACTION READ ONLY`** (`exec::in_read_txn`), so provenance extraction, the rows and a streamed batch sequence all see ONE pinned catalog snapshot — the version a lineage input reports is then the version the read observed. It is also *faster* than the unbracketed read (measured), so it is not gated on lineage. The transaction is rolled back on drop; never leave one open on a pooled connection, and a read that panics must not return its connection to the pool.
- **Errors are classified by DuckDB's error CLASS, never by which call failed** (`src/errclass.rs`). DuckDB decides for itself how much work happens in `prepare()` — it binds `INSERT` there but defers `CREATE TABLE`'s duplicate check to execution — so "prepare failed ⇒ parse error, anything else ⇒ internal" made the agent-facing kind an accident of binder phasing: `INSERT INTO nope` came back as a *syntax* error and `CREATE TABLE t` on an existing `t` as *internal* + "retry". The class prefix (`Parser Error:`, `Syntax Error:`, `Catalog Error:`, `Binder Error:`, `Conversion Error:`, `Constraint Error:`, `IO Error:`, `HTTP Error:`, `Not implemented Error:`, `Invalid Input Error:`, `Out of Range Error:`, `TransactionContext Error:`) is matched at the head of the message and mapped to `EngineError`; anything else stays `Engine` (→ `internal`) rather than borrowing another kind's advice. **The unmapped remainder is a decision, not a default** — the four classes we leave there, and why, are listed on `class_of`. The last four prefixes arrived with Nexus finding 8: `Not implemented Error:` is what DuckLake says to `CREATE TABLE t(id INTEGER PRIMARY KEY)`, and while it fell through to the catch-all an agent was told to retry a statement that can never succeed and then wake an operator who has nothing to fix. Everything DuckLake refuses this way (PK/UNIQUE, CHECK, indexes, sequences, generated columns) is a clause the caller can delete, so it is `unsupported_feature` with the feature name in `facts` — lifted from DuckDB's own sentence, never composed by us. The prefixes carry no stability guarantee, so `engine_e2e.rs::error_contract_duckdb_error_classes_are_unchanged` pins one statement per class — a rename silently drops that whole class back to "retry, report to your operator". Note `INTERRUPT Error` is deliberately NOT a class we key on: `run_with_abort` normalizes it to `Cancelled` and only `Engine` reaches that match.
- **Caller-supplied CATALOG PARAMETERS are classified too, and the two attaches are not the same attach.** `attachers.rs` refuses a plan it cannot build with `EngineError::MissingParameter` / `UnsupportedParameter` (→ `missing_argument` / `invalid_value`, both `agent`/`after_change`), never `Engine`: these messages already say *"requires --option endpoint=<rest-url>"*, and shipping the fix inside `internal` + "Retry; if it persists, report to your operator" is Nexus finding 8's shape at a second site — nothing has reached DuckDB, so there is nothing for an operator to look at. The EXTERNAL catalog's `ATTACH`/`CREATE SECRET` in `duck_engine::run_attach_plan_inner` runs `errclass::classify` for the same reason: the endpoint, warehouse and credentials are the CALLER's, so an unreachable one is `source_unavailable` ("check the path or URL"), not a fault of ours. Nothing is lost, because `classify`'s catch-all is still `Engine`. **The pond's own attach (`instance::PondInstance::open`) deliberately stays unclassified** — that path is ours, and `source_unavailable`'s advice names a statement the caller never wrote. Pinned by `duck_engine.rs::error_contract_a_bad_external_catalog_address_is_not_our_failure` (a real unreachable path, not a fabricated error) and — for the iceberg half, which needs a real HTTP server and so cannot run offline — by `admin.rs::error_contract_an_iceberg_endpoint_that_is_not_a_catalog_is_not_our_failure`.
- **An ATTACHED CATALOG is engine state, and it lives on the `Pond`.** `attach_catalog` mounts an external catalog on the pond's instance and LEAVES it mounted, because two attached at once is what lets one ordinary `write_query` JOIN across them — the removed transient `pull_catalog` attached and detached inside a single call and could never have two. The record (`Pond::attached`) holds each `AttachPlan`, not just its description, because teardown needs the SECRET NAMES it created; rebuilding them at detach would mean holding the credential for the attachment's life. It is NOT persisted: a node restart loses every attachment, and the recovery is an error an agent can act on (below), not a stored table. DuckDB's `ATTACH` is database-level, so a catalog mounted on the writer is visible to every pooled read connection — which is exactly why the record belongs on the `Pond` and dies with it (`forget_pond`, a re-tier).
- **A statement naming a catalog nobody attached is re-classified, from OUR record.** `duck_engine::name_missing_catalog` turns DuckDB's `Catalog "lake" does not exist!` into `EngineError::CatalogNotAttached { name }` — but only when the named alias is neither attached nor the pond's own, which is a check only the engine can make. Left as a plain catalog error, the advice an agent gets is "look up what the pond has — describe_pond, SHOW TABLES", which lists nothing called `lake` and never mentions `attach_catalog`. A two-part `lake.orders` is deliberately left alone: DuckDB reports that as a missing SCHEMA, which a schema typo produces too.
- **A credential reaches DuckDB through a NAMED SECRET and nothing else.** `latiq_common::Secret` masks `Debug`/`Display`/`Serialize` and has exactly two `expose()` sites in the workspace (this crate's `attachers.rs`, and the node-to-node forward that carries a credential to the node that builds the statement); `latiq_common::secret::secret_is_exposed_only_where_it_has_to_be` pins that set by file. The `ATTACH` only ever NAMES a secret, because the attach is the statement whose failure is classified, retried and logged — pinned by `attachers.rs::a_credential_never_leaves_the_create_secret_statement`, over every type and every credential it declares. A surface-level containment test cannot catch this: DuckDB's errors do not echo the statement, so a token in the `ATTACH` passes every envelope check while sitting one `format!` away from a log line.
- **The read guard has THREE answers, not two** (`latiq_engine::classify`): `Write` (refuse — `read_only_violation`), `Read`, and `Unrecognized`, which goes to the parser. `is_read_only`'s old boolean called a typo a write, so `read_query "SELEKT * FROM t"` told the agent to use `write_query`. `Unrecognized` is safe because the read paths run inside `BEGIN TRANSACTION READ ONLY` — the engine refuses a write there — but the leading-keyword list still names every non-read statement word (incl. `SET`/`USE`/`COMMENT`, which the contained-keyword scan cannot carry) so real writes are still refused by name.
- **Explain estimates come from `EXPLAIN (FORMAT JSON)`** (`src/explain.rs`), never from parsing the box-drawing text. `estimated_rows` is the ROOT operator's `Estimated Cardinality` (falling back to the nearest descendant that has one — an `ORDER_BY` root carries none, and reporting 0 would read as "returns nothing"); `scan_operations` is every operator naming a `Table`; `warnings`/`suggestions` are DERIVED from an unfiltered scan over `FULL_SCAN_WARN_ROWS`, and a `Filters` value prefixed `optional:` is a synthesised dynamic filter, NOT the agent's predicate. **Parsing must never fail the call** — an unreadable plan returns `raw_plan` with empty estimates and a log line, because an explain that errors is worse than one that under-reports. The plan JSON is a serialisation internal with no stability guarantee, so `engine_e2e.rs::explain_plan_key_names_still_match_this_duckdb_version` pins the five keys we read. **This is not a lineage source** — the JSON plan emits bare table names for DuckLake scans and conflates catalogs, which is exactly why extraction uses the bound plan; do not reuse it for provenance. There is deliberately no `estimated_bytes`/`estimated_duration_ms`: the plan has neither, and a permanently-zero field reads as "this query is free".
- **Cell conversion is ours:** `cell_to_json` must not silently truncate (e.g. `HugeInt`/i128 → encode as string when outside i64 range, never `as i64`).

## duckdb-rs facts that shape the code (confirmed against the real crate)
These are the non-obvious ones — they explain shapes here that otherwise look arbitrary.
- **ATTACH is `ATTACH 'ducklake:duckdb:<catalog.duckdb>' AS pond (DATA_PATH '<dir>')`** — the `ducklake:duckdb:` prefix is load-bearing, `DATA_PATH` is where the Parquet lands, and `AS pond` is the alias every later statement qualifies with. `INSTALL ducklake` needs the extension repo, so the image bakes extensions in (`latiq warm-extensions`) rather than reaching out at runtime.
- **`Connection` is NOT `Send`** (`RefCell` inside). It can never be shared across threads or held across an `.await` — hence `spawn_blocking` + a connection owned by the thread that runs the query. Cancellation works because `conn.interrupt_handle()` returns an `Arc<InterruptHandle>` that *is* `Send + Sync`: take the handle **before** moving the connection, park it in the in-flight registry, call `.interrupt()` from anywhere (abort lands in <10ms; the error is `INTERRUPT Error: Interrupted!`). There is no `Connection::interrupt()`.
- **`Statement::column_names()` panics before the statement has executed** (the schema is `None` until then). Read it as `r.as_ref().column_names()` from inside the row closure, or after `query_map`/`query_row`.
- **Attribution is native and needs no help:** `CALL pond.set_commit_message(author, op, extra_info => …)` inside the transaction populates the `author` column of `pond.snapshots()` (`snapshot_id`/`author`/`commit_message`); `ducklake_snapshots('pond')` is the same thing. Snapshots from unattributed statements carry `author = NULL` — that is the tell that a caller closed our transaction early, and it is now the ONLY way to produce one. The other producer used to be the special-cased `pull_catalog`: it ran its `CREATE TABLE … AS SELECT` straight on the writer connection with no bracket, so data entered the pond through the one path with nobody recorded as having put it there (measured: `(1, NULL, NULL)` in `ducklake_snapshots`). That op no longer exists — an extract is an ordinary `write_query` against an attached catalog, and is attributed by the one bracket every write goes through.

## Testing philosophy
**Do not test DuckDB.** It's a production engine. Test *our* integration only: the guards, attribution plumbing (native `pond.snapshots()`), cell conversion, cancellation + resource release, and concurrency correctness. Unit + `tests/engine_e2e.rs`.
