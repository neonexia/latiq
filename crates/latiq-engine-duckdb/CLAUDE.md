# latiq-engine-duckdb — CLAUDE.md

The DuckDB + DuckLake implementation of `QueryEngine`.

## Invariants
- **One DuckDB instance per pond** — mutex-guarded, reused across queries (cached in `DuckEngine.instances` keyed by `catalog_uri`). It's the unit of **resource isolation** (per-pond memory/CPU caps belong on the instance — DuckDB's `memory_limit`/`threads` are instance-global) and of concurrency ownership (one process owns each catalog file; independent instances racing on one catalog lose writes). NEVER revert to instance-per-query. (See the concurrency test.)
- **Attribution records provenance, not just a name.** The commit `author` is the **verified `subject`** when `identity.verified`, the claimed `agent_id` otherwise; the claimed leaf + `issuer` + `verified` always ride in `commit_extra_info` as JSON built with `serde_json` (never hand-concatenated — every value is caller- or token-supplied). A bare `verified` must never sit next to a claimed value.
- **Pure DuckLake — nothing on top.** Attribution = native `CALL pond.set_commit_message(author, 'write_query', extra_info => …)`. Callers read history via native `pond.snapshots()` and tables/columns via `SHOW TABLES`/`information_schema`. **Create NO Latiq objects in the pond catalog** — no `_latiq` schema, views, or macros — and no shadow store. (`describe_schema` may use `duckdb_tables()` *internally* — that's the DuckDB adapter's own introspection, not an object in the pond.)
- **Write path must isolate user SQL from our framing.** Don't build a single string batch of `BEGIN; <user sql>; CALL set_commit_message; COMMIT` — user comments/`;` can comment out the COMMIT/attribution or inject statements. Execute user SQL as its own statement, then our `set_commit_message`, then COMMIT, and ROLLBACK on error. Our attribution call must be last so it can't be forged. Caller SQL that does its own `BEGIN`/`COMMIT`/`ROLLBACK`/`START TRANSACTION` closes our bracket early and the snapshot lands with **no author** — that is a **documented contract, not an enforced one**: the write path does **not** scan or classify SQL and must not start (the read guard's keyword scan exists for the read bracket only — don't mirror it here). The guidance lives on the agent-facing surfaces (`latiq-mcp` tool descriptions + `latiq://guidance`/`latiq://dialect`/`latiq://recipes/attribution-lookup`) and in `docs/identity.md`.
- **Cancellation = `Connection::interrupt_handle()`** from a watcher thread; on abort, interrupt + (for safety) discard/reset so a stale interrupt can't bleed into the next query on the reused connection. `abort` must release engine resources promptly (the cancellation test is the gate).
- **`drop_pond` must evict the cached instance** (close the connection) — or it leaks fds/connections to deleted catalog files.
- **Read/write/explain guards are ours.** `read_query` must reject writes (incl. `WITH … INSERT`); `explain_query` must NOT execute (`EXPLAIN ANALYZE` runs the statement — reject it). DuckDB exposes no statement-type introspection, so these are careful heuristics — test the edge cases. The keyword scan treats `;` as a separator (without it `SELECT 1;INSERT …` passed as a read and the insert *ran*), and rejects **transaction control** (`BEGIN`/`COMMIT`/`ROLLBACK`/`ABORT`/`START TRANSACTION`/`END TRANSACTION`) because user SQL must not be able to close the bracket below. Bare `END`/`START` stay allowed on purpose — `CASE … END`.
- **The two read paths run inside `BEGIN TRANSACTION READ ONLY`** (`exec::in_read_txn`), so provenance extraction, the rows and a streamed batch sequence all see ONE pinned catalog snapshot — the version a lineage input reports is then the version the read observed. It is also *faster* than the unbracketed read (measured), so it is not gated on lineage. The transaction is rolled back on drop; never leave one open on a pooled connection, and a read that panics must not return its connection to the pool.
- **Cell conversion is ours:** `cell_to_json` must not silently truncate (e.g. `HugeInt`/i128 → encode as string when outside i64 range, never `as i64`).

## duckdb-rs facts that shape the code (confirmed against the real crate)
These are the non-obvious ones — they explain shapes here that otherwise look arbitrary.
- **ATTACH is `ATTACH 'ducklake:duckdb:<catalog.duckdb>' AS pond (DATA_PATH '<dir>')`** — the `ducklake:duckdb:` prefix is load-bearing, `DATA_PATH` is where the Parquet lands, and `AS pond` is the alias every later statement qualifies with. `INSTALL ducklake` needs the extension repo, so the image bakes extensions in (`latiq warm-extensions`) rather than reaching out at runtime.
- **`Connection` is NOT `Send`** (`RefCell` inside). It can never be shared across threads or held across an `.await` — hence `spawn_blocking` + a connection owned by the thread that runs the query. Cancellation works because `conn.interrupt_handle()` returns an `Arc<InterruptHandle>` that *is* `Send + Sync`: take the handle **before** moving the connection, park it in the in-flight registry, call `.interrupt()` from anywhere (abort lands in <10ms; the error is `INTERRUPT Error: Interrupted!`). There is no `Connection::interrupt()`.
- **`Statement::column_names()` panics before the statement has executed** (the schema is `None` until then). Read it as `r.as_ref().column_names()` from inside the row closure, or after `query_map`/`query_row`.
- **Attribution is native and needs no help:** `CALL pond.set_commit_message(author, op, extra_info => …)` inside the transaction populates the `author` column of `pond.snapshots()` (`snapshot_id`/`author`/`commit_message`); `ducklake_snapshots('pond')` is the same thing. Snapshots from unattributed statements carry `author = NULL` — that is the tell that a caller closed our transaction early.

## Testing philosophy
**Do not test DuckDB.** It's a production engine. Test *our* integration only: the guards, attribution plumbing (native `pond.snapshots()`), cell conversion, cancellation + resource release, and concurrency correctness. Unit + `tests/engine_e2e.rs`.
